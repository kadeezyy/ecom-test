# Ядро магазина цифровых товаров

Бэкенд-ядро площадки цифровых товаров: заказы, платёжные вебхуки, автоматическая
выдача кодов через двух поставщиков, сверка и витрина каталога.

Стек: **Python 3.11+ · FastAPI · PostgreSQL 16 · SQLAlchemy 2.0 (async) · Alembic ·
httpx · structlog**. Очередь фоновых задач — в самой БД, внешнего брокера нет.

---

## Коротко о главном

Задание построено вокруг одной проблемы: **таймаут ≠ отказ**. Всё остальное —
следствие. Три решения, которые держат надёжность:

**1. Идемпотентность вебхука обеспечивает БД, а не код.**
`payment_events.event_id` — первичный ключ, приём делается через
`INSERT … ON CONFLICT DO NOTHING`. Между «проверить, что события ещё нет» и
«вставить» у конкурентов была бы гонка; у атомарной вставки её нет. Дальше —
`SELECT … FOR UPDATE` по заказу, поэтому 50 параллельных событий выстраиваются в
очередь на строке, а перейти `created → paid` может только первое.

**2. `request_id` детерминирован и не зависит от номера попытки.**
`request_id = req_{order_id}_{supplier}`. Любой повтор к тому же поставщику идёт с
тем же идентификатором, а контракт обязывает поставщика вернуть на него **тот же
код**. Отдельного «сверочного» вызова не нужно: повторный `POST /issue` и есть
сверка. Последний рубеж — частичный уникальный индекс
`deliveries(order_id) WHERE status='succeeded'`: двух успешных выдач на заказ не
может быть даже при ошибке в логике.

**3. Исход попытки трёхзначный, и фолбэк разрешён только из одного из них.**

| Что случилось | Класс | Почему | Фолбэк на B |
|---|---|---|---|
| `{"status":"ok", "code": …}` | успех | — | — |
| `{"status":"error", "reason": …}` (любой HTTP-код) | **доказанный отказ** | приложение поставщика обработало запрос и кода не выдало | ✅ разрешён |
| Ошибка соединения / connect timeout | **доказанный отказ** | TCP-сессии не было — запрос физически не отправлялся | ✅ разрешён |
| Таймаут чтения, обрыв, неразборный ответ | **неизвестность** | запрос дошёл, ответ — нет; код мог быть выдан | ⛔ **запрещён** |

Из «неизвестности» есть ровно один выход — повтор тому же поставщику с тем же
`request_id`, сколько бы это ни заняло. Заказ при этом висит в восстановимом
статусе и виден в отчёте сверки. Именно поэтому в конфиге **раздельные**
`SUPPLIER_CONNECT_TIMEOUT_S` и `SUPPLIER_READ_TIMEOUT_S`: они разводят
доказуемо безопасный случай и опасный.

Правило целиком умещается в одну функцию — [`domain/fallback.py`](src/shop/domain/fallback.py):
*перейти к следующему поставщику можно только из доказанного отказа.*

## Запуск

### Через Docker (рекомендуется)

```bash
cp .env.example .env && make up
```

Поднимаются: PostgreSQL, миграции, сид каталога, API, воркер и две
заглушки-поставщика.

* API и Swagger — <http://localhost:8000/docs>
* Поставщик A — <http://localhost:9001/admin/state>
* Поставщик B — <http://localhost:9002/admin/state>

Нужен PostgreSQL 16 и Python 3.11+.

```bash
make venv
```



## Воспроизведение состязательных сценариев вручную

Скрипт `scripts/flood_webhooks.py` играет роль заглушки платёжной системы —
он же и есть харнесс гонок.

**Гонка: 50 параллельных вебхуков по одному заказу**

```bash
make race
```

Ожидаемый вид вывода:

```
отправлено 50 вебхуков за … c
HTTP-коды:        {200: 50}
applied=true:     1   <- должно быть ровно 1
duplicate=true:   0
причины отказа:   {'already_paid': 49}
статус заказа:    delivered
успешных выдач:   1   <- должно быть ровно 1
```

**Повторная доставка одного `event_id`**

```bash
make race-same-event    # duplicate=true: 49, applied=true: 1
```

**Отказ поставщика A и фолбэк на B**

```bash
make supplier-a-down    # A всегда отвечает контрактной ошибкой
make race               # заказ выдан поставщиком B, ровно один раз
curl -s localhost:9001/admin/state | python3 -m json.tool  # issued_count: 0
curl -s localhost:9002/admin/state | python3 -m json.tool  # issued_count: 1
```

**Ловушка таймаута: A выдал код, но ответ не дошёл**

```bash
make supplier-a-timeout   # A выдаёт код и зависает на 30 c
make race
```

Ожидаемое поведение: заказ **не** переходит в `delivered`, к поставщику B
**не обращаемся**, у A `issued_count == 1`. Дальше:

```bash
curl -sX POST localhost:9001/admin/config -H 'content-type: application/json' -d '{"mode":"ok"}'
curl -sX POST localhost:8000/admin/orders/<ORDER_ID>/retry-delivery -H "X-Admin-Token: dev-admin-token"
```

Повтор уходит тому же поставщику с тем же `request_id`, возвращается **тот же**
код, ключ израсходован один раз.

**Пустой остаток**

```bash
curl -sX POST localhost:9001/admin/drain
curl -sX POST localhost:9002/admin/drain
make race     # заказ -> out_of_stock, не падение
curl -sX POST localhost:9001/admin/restock -H 'content-type: application/json' \
     -d '{"keys":["NEW1-NEW1-NEW1"]}'
# фоновый добиватель сам поднимет заказ в течение SWEEP_INTERVAL_S
```

**Сверка**

```bash
make reconcile
```

## Устройство

```
src/shop/
├── core/          конфиг, логи, исключения, движок БД, идентификаторы
├── domain/        чистые правила: статусы, переходы, фолбэк, деньги
├── models/        ORM-таблицы (без бизнес-логики)
├── repositories/  весь SQL: блокировки, SKIP LOCKED, ON CONFLICT
├── services/      бизнес-логика: заказы, платежи, выдача, сверка, журнал
├── integrations/  HTTP-клиент поставщика
├── api/           тонкий транспорт: роутеры, схемы, обработчики ошибок
└── worker/        фоновый воркер и добиватель зависших заказов

src/supplier_stub/ заглушка поставщика с управляемым хаосом
```

Правило слоёв: роутер валидирует и зовёт сервис; сервис содержит всю логику;
репозиторий содержит весь SQL; модель — только данные.

### Модель данных

| Таблица | Роль | Ключевые ограничения |
|---|---|---|
| `products` | каталог + денормализованный остаток | два частичных покрывающих индекса витрины |
| `orders` | заказ и его статус | `idempotency_key` уникален; `last_payment_event_at` отсекает события вне порядка |
| `payment_events` | вебхуки как есть | PK `event_id` = идемпотентность приёма; FK на `orders` намеренно нет — событие может прийти раньше заказа |
| `deliveries` | попытка выдачи у поставщика | `request_id` уникален; **UNIQUE `(order_id) WHERE status='succeeded'`**; UNIQUE по коду |
| `delivery_jobs` | очередь | **UNIQUE `(order_id) WHERE state IN ('queued','running')`** — одна активная задача на заказ |
| `ledger_entries` | журнал денежных движений | UNIQUE `(order_id, event_type, account)` — проводка не может задвоиться |
| `audit_log` | история переходов | — |

**Журнал денежных движений.** Проводки парные и в сумме нулевые:

* оплата: `gateway` +A, `order_liability` −A
* выдача: `order_liability` +A, `revenue` −A

Отсюда два полезных следствия: `SUM(amount_minor)` по всей таблице всегда `0`
(это инвариант, который проверяет тест), а ненулевой `order_liability` по заказу
буквально означает «оплачен, но не выдан» — сверка в деньгах, а не только в
статусах.

### Жизненный цикл заказа

```
created ──paid──> paid ──> delivering ──> delivered
   │                            ├──> out_of_stock ───┐  восстановимо
   └──> payment_failed          └──> delivery_failed ─┘  ──> delivering ──> delivered
```

Переходы описаны ровно в одном месте — `domain/transitions.py`. Из финальных
статусов выхода нет: повторный вебхук уже выданного заказа ничего не меняет.

### Восстановление

Три независимых механизма, все идемпотентны:

1. **Повтор в очереди** — неизвестный исход перепланируется с экспоненциальным
   бэкоффом и джиттером, всегда к тому же поставщику.
2. **Добиватель** (`worker/jobs.py`) — раз в `SWEEP_INTERVAL_S` возвращает в
   очередь задачи умершего воркера, поднимает оплаченные-но-не-выданные заказы
   без активной задачи и доигрывает «осиротевшие» платёжные события.
3. **Ручной повтор** — `POST /admin/orders/{id}/retry-delivery`.

При подготовке к повтору сбрасываются **только** доказанные отказы: после
пополнения остатка к поставщику A можно обратиться снова. Строки со статусом
`unknown` не трогаются — иначе потерялась бы привязка «повторяем тому же».

### Логи

structlog, JSON, у каждой записи поле `event` — стабильный машиночитаемый ключ
(`payment_webhook_received`, `delivery_outcome_unknown`, `delivery_completed`).
Текст сообщения ключом поиска не является. Сквозные поля: `order_id`,
`event_id`, `request_id`, `supplier`, `attempt`. Все ERROR пишутся с объектом
исключения, поэтому в логе есть traceback.

```json
{"event":"delivery_outcome_unknown","level":"error","order_id":"ord_ab12","supplier":"a",
 "request_id":"req_ord_ab12_a","reason":"read_timeout","attempt":1,"fallback_blocked":true,
 "exception":"Traceback (most recent call last): ...","timestamp":"2026-01-01T12:00:00Z"}
```

## Этап 5: каталог под нагрузкой

Витрине нужен один запрос: «активные товары с ненулевым остатком, по цене,
первые N». Остаток живёт у поставщика, но ходить туда на каждый запрос нельзя —
поэтому он денормализован в `products.available_count` и обновляется фоновой
синхронизацией (только по тем SKU, что реально обслуживают поставщики, и только
при изменении значения).

Под этот запрос — два **частичных покрывающих** индекса:

```sql
CREATE INDEX ix_products_shelf ON products (price_minor, sku)
  INCLUDE (name, type, currency, available_count)
  WHERE is_active AND available_count > 0;

CREATE INDEX ix_products_shelf_by_type ON products (type, price_minor, sku)
  INCLUDE (name, currency, available_count)
  WHERE is_active AND available_count > 0;
```

Почему именно так:

* **партиальность** выкидывает из индекса неактивные и распроданные SKU — индекс
  меньше самой «горячей» части данных и не растёт от архива;
* **`INCLUDE`** доносит все выбираемые колонки, поэтому скан идёт `Index Only Scan`
  — без обращения к куче;
* **порядок `(price_minor, sku)`** совпадает с `ORDER BY`, поэтому узла `Sort` в
  плане нет вообще, а `LIMIT` останавливает скан после N строк: время ответа не
  зависит от размера каталога;
* **курсорная пагинация** `(price_minor, sku) > (:price, :sku)` вместо `OFFSET` —
  `OFFSET` заставил бы читать и выбрасывать все пропущенные строки, и последняя
  страница стоила бы дороже первой.

Посмотреть план:

```bash
make seed-bulk    # 50 000 SKU
make explain
```

Тесты `tests/perf/` проверяют не время (оно шумит), а форму плана: индекс
использован, `Seq Scan` отсутствует, сортировки нет.

## Как масштабировали бы дальше

* **Воркеры.** `FOR UPDATE SKIP LOCKED` уже даёт горизонтальное масштабирование:
  N процессов забирают непересекающиеся пачки без брокера. Первый предел —
  нагрузка на таблицу очереди; лечится партиционированием `delivery_jobs` по дате
  и переносом «мёртвых» задач в архив.
* **Брокер.** Внешняя очередь (Kafka/NATS) появится тогда, когда задачи
  перестанут быть частью той же транзакции, что и смена статуса заказа. Пока это
  условие держится, БД-очередь надёжнее: нет двухфазной проблемы «записали в
  брокер, но откатили транзакцию». Переход — через outbox.
* **Вебхуки.** Приём вебхука сейчас делает одну вставку и один блокирующий
  `SELECT`. Под большим потоком стоит разделить: писать событие и отвечать 200,
  а применение к заказу отдать тому же воркеру. Контракт не изменится.
* **Каталог.** Витрина уже index-only. Дальше — реплика для чтения и кэш
  первых страниц; инвалидация по `stock_updated_at`.
* **Поставщики.** Цепочка `A → B` вынесена в чистую функцию; добавить третьего —
  это дописать его в `SUPPLIER_CHAIN`. Осмысленное следующее улучшение —
  circuit breaker на доказанных отказах, чтобы не тратить попытки на лежащего
  поставщика (`SupplierRegistry.replace` для этого уже есть).

## Принятые допущения

1. **Стек — Python**, хотя в ТЗ приоритет Node.js/PHP (ТЗ допускает «Python, Go и
   другие»). Выбор согласован до начала работы.
2. **Склад ключей живёт у поставщиков**, а не у нас: по контракту код выдаёт
   поставщик. 50 ключей из задания поделены между A и B без пересечений (25/25).
   Пул общий на все SKU, поэтому остаток одинаков для всех товаров; для этапа 5
   сид генерирует разные остатки.
3. **Валюта одна — RUB**, пересчёта нет (в ТЗ переключатель валют объявлен
   декоративным). Внутри суммы хранятся в копейках целым числом; на границе API
   используется формат контракта — целые рубли.
4. **Расхождение суммы вебхука с заказом** не переводит заказ в `paid`: событие
   сохраняется, пишется ERROR-лог, заказ попадает в разбор. Ответ платёжной
   системе всё равно `200` — повтор такое не починит.
5. **Вебхуки вне порядка** разруливаются по `created_at` из полезной нагрузки:
   событие старше уже применённого игнорируется как `stale_event`.
6. **Подпись вебхука не проверяется** — ТЗ явно освобождает. Админские
   эндпоинты закрыты статическим токеном из окружения.
7. **Ответ `200` на вебхук** означает «событие принято на хранение», а не «заказ
   изменён». `5xx` возвращается только при сбое, который повтор действительно
   может починить.
8. **Заглушки поставщиков держат состояние в памяти** и не переживают
   перезапуск — это тестовые двойники, а не сервисы с данными.
9. **Статусы БД — `VARCHAR`, а не нативные `ENUM`**: значения проверяются в
   домене, а миграции при добавлении статуса остаются тривиальными.

## Что осознанно не сделано

* **Circuit breaker** на поставщиков — в требованиях нет, а без него поведение
  проще и предсказуемее. Место для него подготовлено.
* **Внешний брокер очередей** — см. раздел про масштабирование: пока задача
  ставится в одной транзакции со сменой статуса, БД-очередь строго надёжнее.
* **Аутентификация покупателей, корзина, фронтенд** — вне ядра, ТЗ явно
  исключает фронтенд.
* **Мультивалютность и пересчёт цен** — ТЗ говорит, что переключатель валют в
  макете декоративный.
* **Плагинная система поставщиков** — их ровно два, абстракция «на будущее» без
  требования только запутала бы.
* **Метрики Prometheus / трассировка** — в критериях приёмки нет; наблюдаемость
  закрыта структурными логами, аудитом и эндпоинтом сверки.
* **CI-пайплайн** — ТЗ называет инфраструктуру необязательной; `make lint` и
  `make test` готовы к тому, чтобы стать двумя шагами workflow.
